# 视界巡警：后续优化实施方案

更新：2026-09-27。目标设备为一台大华 DH-IPC-HFW4443T-AS-P 固定枪机。比赛演示以“摄像头取流 → 本机 YOLO 人车检测／受控异物基线比对 → 告警截图 → 手动录像 → 关联回放”为主线。以下项目按依赖顺序实施；每一阶段通过验收后再进入下一阶段。

## 现状与边界

- 前端已完成路由分包、页面卸载清理、基本响应式布局、录像页外部图标与播放器脚本清理。构建通过不等于实机演示通过。
- YOLO 模型当前识别 `person`、`car`；异物遗留是固定机位、同背景和相对稳定光照下的图像差分原型。摄像头本身不运行这些识别算法。
- 手动录像、录像索引、按摄像头及告警时刻匹配录像已有代码，但尚缺实机全链路及长时间回归记录。
- C 盘在最近一次检查中可用空间为 0；必须先恢复充足空间并重新确认剩余容量，避免浏览器缓存、数据库和构建因磁盘写入失败干扰验收。清理范围由使用者确认，不能自动删除未知文件。

## 阶段 0：建立可复现的演示环境（P0）

1. 检查 MySQL、Java、Python 检测服务、前端端口和枪机 IP／RTSP；把可配置项集中到本地配置模板，脚本只引用模板或环境变量，不散落硬编码。
2. 扩展 `start_demo.ps1`：顺序检测依赖、端口占用、模型文件、数据库迁移、录像目录可写性、磁盘余量；失败时给出明确修复提示和非零退出码。
3. 保存版本清单、模型文件散列值、阈值、设备位置、显示器亮度、ROI 和基准图；正式演示前保存数据库备份与当前配置，保证测试可复现。

**验收：**一台新启动的演示电脑按操作单启动后，服务健康状态全部可见；缺任一依赖时能定位故障。记录启动日期、配置与构建版本。

## 阶段 1：收敛摄像头状态连接及故障恢复（P0）

涉及 `station-monitoring-frontend/src/views/HomePage.vue`、`MonitoringScreen.vue`、`CameraManagement.vue`、`src/views/ImageDetection.vue` 与 Java 的 `/ws/cameraStatus`。

1. 建一个共享的摄像头状态客户端：统一生成 WebSocket 地址，开发环境经前端代理转发，兼容当前浏览器协议与主机名；页面订阅同一状态源，最后一个订阅者离开时关闭连接。
2. 对连接、断开、重连定义明确状态；断线后按递增间隔重试，设上限并加轻微随机延迟，防止三个页面同时反复连接；恢复后主动拉取摄像头列表快照再接增量消息。
3. 后端状态消息包含摄像头 ID、状态、时间与原因；前端只覆盖对应设备，忽略过期消息，避免刚恢复在线又被旧消息改为离线。
4. 预览、检测页分别处理设备离线、Java 服务断开、YOLO 服务停止；展示原因、当前动作与“重试”入口。摄像头恢复后不自动创建重复检测任务。

**验收：**浏览器切换三页不会产生三条重复状态连接；拔网线、恢复网络、重启 Java 后，状态在可记录的时间内恢复且显示正确；刷新页面能读到当前状态。记录网络日志和错误截图。

## 阶段 2：把录像、告警、截图做成可核查的闭环（P0）

涉及 `RecordingController.java`、`MonitoringScreen.vue`、`ImageDetection.vue`、`Alarm.vue`、`AlarmRecord.vue`、`video.vue` 与录像索引表。

1. 上传时在前端固定记录摄像头 ID、录制开始与结束时间、文件类型和来源；服务器验证时间顺序、文件大小及实际媒体类型。文件与索引写入要么同时成功，要么明确回滚；失败时保留用户可下载的本地文件。
2. 录像列表读取失败要返回错误状态和可识别错误码；不再把数据库或目录异常吞掉后伪装成“空列表”。前端区分“确实无录像”“加载失败”“只有历史无元数据录像”。
3. 回放改为分块输出而非 `byte[]` 整段读取；完整支持普通请求、`Range` 拖动、非法范围的 416 返回，限制并发和单次读取量。历史录像只显示真实已知的元数据。
4. 告警记录增加来源或通过检测事件关联明确标示“实时模型／受控异物原型／人工导入／历史测试”；展示告警时间、摄像头、类型、处理状态、截图和匹配录像结果。没有覆盖告警时刻的录像时说明原因。
5. 录像操作按权限控制；删除前确认并记录操作者与时间。正式演示数据与历史脚本生成的数据分开筛选，不修改历史记录以伪造实时结果。

**验收：**开始手动录制 → 人进入 ROI 后产生一条告警及截图 → 停止录制并上传 → 点击告警进入对应录像 → 正常播放并拖动进度条。再分别断开 Java、制造上传失败、删除录像文件，确认页面给出正确状态且没有“已入库”的错误提示。

## 阶段 3：检测任务与算法原型稳态化（P0）

涉及 `scan/Detection/detection_service.py`、`ImageDetection.vue` 和区域规则／异物基准表。

1. 每摄像头最多一个 worker；重复点击启动返回当前任务，停止后释放 RTSP、推理和流响应资源。刷新页面通过状态接口恢复按钮状态；仅切换页面不停止任务。
2. 明确任务状态为“未启动、连接中、检测中、摄像头离线、模型不可用、规则失效、停止中”。RTSP 断线后有受控重试和错误原因；持续失败可手动重启任务。
3. 人车分别校验 ROI、置信度、停留时间和告警冷却。持续停留同一目标不刷屏，目标离开再进入后按规则重新触发。把阈值与模型版本写入测试记录。
4. 异物基准记录采集时间、摄像头、分辨率、ROI 和环境条件；机位或光照明显变化时提示重新采集，不能把整屏变化算成异物识别。页面持续标注“受控场景原型”。
5. 健康检查分别报告模型、数据库、摄像头、worker 状态；错误消息给出下一步操作，不只显示“连接失败”。

**验收：**空场景 30 秒无目标告警；人员与车辆场景分别记录真实检测结果；同一目标持续停留只产生符合规则的一条事件；切换页面、刷新、断线恢复、停止后可再次启动。异物测试必须使用相同背景的空场景和新增物体画面。

## 阶段 4：实机回归与故障演练（P0，比赛交付门槛）

1. 固定枪机对准显示器，按 `DEMO_RUNBOOK.md` 依次测试空场景、人员、车辆和受控异物。每项保存原始画面、阈值、告警截图、录像文件及实际结果；失败也如实记录。
2. 连续运行至少 30 分钟，每 5 分钟记录画面、任务数量、CPU／内存、告警数、连接数和磁盘余量；期间执行一次断网恢复与一次服务重启。
3. 用独立浏览器会话走登录、导航、预览、检测、告警、录像回放，检查页面切换是否卡顿，视频是否自动暂停或泄露资源。
4. 形成一页实测报告：通过／失败、重现步骤、截图、构建版本和未解决问题。比赛材料只能引用这里实际验证过的结果。

**验收：**核心链路可现场重复演示两次；无重复 worker、无意外假告警、录像可播放拖动；所有失败点有可操作提示。若其中任一项不通过，先修复再进入外观优化。

## 阶段 5：页面体验和导航收敛（P1）

涉及 `Sidebar.vue`、`HomePage.vue`、`MonitoringScreen.vue`、`ImageDetection.vue`、`Alarm.vue`、`video.vue`。

1. 给“实时预览 → 智能检测 → 告警 → 视频回放”一致的入口、面包屑和返回路径；告警卡片直接打开截图及相关录像。固定枪机无机械云台、光学变焦、聚焦、光圈时不展示这些控件；数字缩放写明是浏览器画面操作。
2. 统一状态词、图标、颜色、空态和错误态；颜色之外保留文字与图标，错误在相应区域显示并提供重试按钮。长任务显示加载状态，按钮防重复提交。
3. 控制页面层级、滚动区域和表格高度；检查 320、768、1024、1440 像素布局。输入框有标签、图片有说明、键盘焦点可见，动态错误可被读屏提示。
4. 比赛演示导航可提供清晰的“核心流程”分组；球机预置点、股道和道岔等当前实机不支持的项目移至“其他功能”或在演示模式下隐藏，但保留原功能入口与数据。

**验收：**四页可按自然顺序完成任务；无横向溢出或控件遮挡；键盘可完成主要操作；设备不支持的控制不会诱导用户点击。截图人工核对，而非仅以编译通过为准。

## 阶段 6：性能与容量（P1）

1. 先量化本机登录首屏、四个核心路由切换、预览首帧、检测首帧、录像列表和拖动响应；每项测 10 次，保留中位数及最大值、硬件与浏览器版本。
2. 分析构建产物；按需加载 ECharts、播放器 SDK 和非核心页面，减少全局组件及重复轮询。图表、媒体流、定时器和 WebSocket 在退出页面时逐项释放。
3. 录像列表在文件数量增多时改为服务端分页／筛选；避免一次扫描及传输全部文件。设置录像、截图和日志的保留策略与磁盘告警，禁止演示过程中静默清理证据。
4. 用同一演示电脑、同一测试数据比较优化前后指标；只保留能改善实测卡顿的改动。

**验收：**连续切换核心四页 20 次，不出现不断增长的连接、定时器或内存；性能报告包含真实测量值，不把打包大小当作页面加载时间。

## 阶段 7：自动化测试和数据迁移（P1）

1. Java 增加录像上传、索引失败、列表错误、时间匹配、Range 206／416、鉴权和删除权限测试；测试库与真实演示库隔离。
2. Python 用可控图片与模拟 RTSP 输入测试单 worker、启动／停止、断线重连、ROI 驻留、告警去重、基准失效和截图路径；不依赖实机才能跑单元测试。
3. 前端增加核心路由及关键状态的冒烟测试：未登录跳转、服务离线提示、上传失败本地文件、告警跳转回放。
4. 把建表逻辑整理为可追踪 SQL 迁移文件，增加备份、迁移和回滚说明；禁止直接在唯一演示数据上试验不可逆迁移。

**验收：**自动测试在干净环境重跑通过；迁移能从已有数据库版本升级，并能按备份恢复。实机回归仍单独执行。

## 阶段 8：安全与可部署性（P2；一旦接入校园网或公网需提前）

1. `UserController.java` 中的 Base64 密码改为带盐的单向哈希，登录时兼容存量账户并在成功验证后迁移；覆盖注册、登录、改密和回滚。
2. `CameraController.java` 不再将设备密码随摄像头列表返回给浏览器；逐步把浏览器直连设备改为受认证的后端媒体代理或安全网关。此项需要评估现有大华 SDK／播放器协议兼容性。
3. `/ws/cameraStatus` 握手验证会话并限制允许来源，取消通配符 `*`；检测服务经同源代理或服务间认证访问，避免任何本机进程都可创建任务和读取证据。
4. 敏感配置移至环境变量或受控配置文件；日志不记录账号密码、设备密码、token；按角色限制录像删除、设备修改、规则配置。
5. 统一配置项、数据库迁移和启动方式，形成离线安装与故障恢复手册。公网或现场部署前进行一次权限与数据流审查。

**验收：**浏览器网络响应中看不到摄像头密码；未认证用户无法读取视频、截图、告警或通过 WebSocket 收到状态；存量账号登录后可平滑迁移且新注册密码不再可逆。

## 阶段 9：模型效果验证与长期扩展（P2）

1. 对 `person`、`car` 建立有授权、按场景划分的独立测试集，记录漏报、误报、不同光照／角度下的表现和推理耗时；训练集与测试集不重复。
2. 异物原型单独测试基准变化敏感度，不使用人车模型指标替代。只有完成数据收集、标注、训练和独立测试后，才扩展为具体异物类别识别。
3. 若将来增加多摄像头、自动告警录像或边缘部署，先重估硬件、带宽、存储与隐私授权，再设计任务调度和权限；当前比赛版本保持单枪机、手动录像边界。

**验收：**每项对外指标都能对应测试集、评测脚本、版本和原始结果；商业计划书与现场演示使用同一能力口径。

## 实施顺序与停止条件

`阶段 0 → 1 → 2 → 3 → 4` 是比赛前必须完成的闭环；`阶段 5 → 6 → 7` 改善使用体验和可维护性；`阶段 8 → 9` 为后续联网部署与能力扩展。若比赛前时间不足，优先保住阶段 0～4，尤其是告警与录像的可核查证据。任何阶段发现真实摄像头无法取流、告警不可追溯或录像无法播放时，暂停后续外观与模型扩展，先修复闭环。
